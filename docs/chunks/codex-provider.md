# Codex backend integration

Decision (2026-09-10): use the installed Codex app server over stdio. The CLI
already reports a ChatGPT login. No subscription or credits will be purchased.
The overnight request authorizes this decision and implementation without the
usual intermediate design review.

The reference is local T3 Code at `d081ab7ab`, especially
`apps/server/src/provider/Layers/CodexSessionRuntime.ts` and
`apps/server/src/provider/acp/GrokAcpSupport.ts`. Both providers own their tools,
stream output, and persist conversations. Grok 1.0.24 uses ACP with cached-token
or API-key authentication; T3 adds xAI completion extensions and cancel/continue
coordination for steering. Codex 0.153.4 has direct thread resume, turn steering,
interrupt, and approval RPCs. Its known local login and more direct lifecycle
make it the smaller integration here.

Implement an Effect-scoped stdio transport, normalized event translator, and
Agent adapter. Each turn gets a process; idle threads have none. Resume uses a
provider-specific persisted pointer, leaving existing Claude pointers intact.
This trades warm-start latency for a smaller lifecycle with deterministic cleanup.
Select with `JETTY_AGENT=codex`; keep Claude as the default and echo for tests.
No frontend or jetty-design changes. Codex owns authentication; Jetty never reads
or copies its credentials. Explicit permission modes map to Codex sandbox modes.
Unsupported server requests fail closed rather than hanging or granting access.

Validation will cover protocol framing, translation, approvals, steering,
interrupt/crash/shutdown, persistence, and real Effect RPC. Live checks are opt-in
and separate from deterministic fixtures. Results and walkthrough follow below.

Protocol reference: https://learn.chatgpt.com/docs/app-server (also checked against
bindings generated by the installed CLI).

## Comparison and resulting behavior

| Concern            | Codex                                                             | Grok                                                                                               |
| ------------------ | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Local availability | CLI 0.153.4; `codex login status` confirms ChatGPT login          | CLI 1.0.24; `grok models` reports grok.com login, but its network lookup failed inside the sandbox |
| Effort             | Small stdio JSON-RPC transport and translator; fits Effect scopes | ACP transport and translator, plus Grok extensions and cancellation/continuation coordination      |
| Streaming/tools    | Item start, deltas, authoritative completion; CLI runs tools      | ACP session updates; CLI runs tools                                                                |
| Lifecycle          | Persisted thread ID; explicit start/resume/steer/interrupt        | ACP session load/resume and prompt/cancel; T3 handles more completion edge cases                   |
| Verification       | Real authenticated backend smoke passed                           | Login and source inspected; no model turn attempted                                                |

The shared Agent interface and wire schemas are unchanged. `auto` maps to
workspace-write with on-request approvals; `plan` uses read-only plus a planning
instruction; `full_access` explicitly requests full access without approvals.
These are provider mappings, not identical Claude semantics. Switching out of
plan mode clears Jetty's planning instruction. Requests go to the user approval
route, and allow/deny is one-shot: persistent permission amendments are not sent.

Each thread has independent Codex state in `provider_sessions` (migration 003).
Claude's `threads.agent_session_id` stays intact. Missing Codex transcripts fail
visibly; the adapter does not silently create an empty replacement conversation.
Processes, readers, pending requests, and turns are owned by Effect scopes. A
client disconnect does not own or cancel the turn. Startup/RPC requests have a
30-second deadline; model generation has no artificial total-turn timeout.
Interruption allows two seconds for the RPC acknowledgement, then closes the
process scope (with a one-second force-kill fallback).

## Files worth reading

1. `server/src/codex.ts`: Agent implementation, permissions, session lifecycle,
   approval/question routing, and serialization of publication with steering.
2. `server/src/codex-rpc.ts`: stdio transport using existing Effect dependencies, response correlation,
   framing, request deadlines, and scoped subprocess cleanup.
3. `server/src/codex-translate.ts`: provider items mapped into existing timeline
   events. Final snapshots replace streamed text/output rather than duplicating it.
4. `server/src/db.ts`, `store.ts`, `store.test.ts`: additive provider-pointer storage
   and migration/reopen verification beside the unchanged Claude pointer.
5. `server/src/main.ts`: opt-in `codex` selection; no implicit Claude title generator
   for Codex. `ServerOptions.codex` can inject process settings for embedding/tests.
6. `server/src/codex.test.ts`, `fixtures/codex-peer.ts`, `codex-network.test.ts`,
   `codex-live.test.ts`: protocol fixtures, lifecycle faults, RPC, and opt-in live smoke.

## Validation

- 26 focused fixture tests pass: Unicode/framing, tool output, authoritative final
  text, thread isolation, resume, allow/deny, questions, unsupported requests,
  steering, duplicate starts, missing CLI, startup timeout, crash/malformed output,
  permission/image/effort mapping, scope shutdown, and publication failure races.
- Provider, backend RPC, and migration checks: 44 passed on Bun 1.4.2.
  The RPC fixture checks disconnect/reconnect, steering, durable timeline state,
  immediate next-turn admission, approval denial, and server shutdown. Incomplete
  tool rows are settled on termination, and shutdown persists one terminal event.
- Live test: GPT-6 Astra, medium effort, standard speed; the actual CLI read a
  temporary marker with a shell tool, streamed it through Jetty's WebSocket RPC,
  then recalled it without tools after Jetty restarted using the stored pointer.
  This passed on Bun 1.4.0 (16.7s and 20.8s), then on the required Bun 1.4.2
  (16.6s). Bun 1.4.2 was installed only in a temporary directory; the system
  runtime was unchanged. No subscription, credits, or reset was purchased.
  The fixture folder and server were cleaned up.
- `bun run typecheck` and `bun run lint` pass. Formatting passes for changed files.
  Global `format:check` finds five unchanged files; the identical list reproduces
  on untouched `origin/jetty-v2`: `.zed/settings.json`, `client/src/components/composer.tsx`,
  `server/src/usage.ts`, `server/src/usage.test.ts`, and `shared/tsconfig.json`.
- Final regression runs report 320 passed, 2 skipped, 12 failed on both Bun 1.4.0
  and Bun 1.4.2 (334 tests; the client failures also produce 10 socket errors).
  All 12 failures reproduce on an untouched baseline: ten legacy client-protocol
  tests time out against native Effect RPC, and two HTTP tests assume Linux
  `/proc/self/fd` on this macOS host. Frontend and unrelated HTTP code are unchanged.

Reproduce deterministic provider checks with:

```sh
bun test server/src/codex.test.ts server/src/codex-network.test.ts server/src/store.test.ts
```

Live verification is never enabled by normal tests:

```sh
JETTY_CODEX_LIVE_TEST=1 bun test server/src/codex-live.test.ts
```

## Remaining limits

No frontend wiring or design changes. No warm-process cache, automatic titles,
Codex account quota reporting, or price estimates. Context usage uses the reported
last model-call total and window, without inventing Claude-style category slices
or a compaction threshold. Input images are mapped and fixture-tested; live vision
was not tested. Approval/steering fault paths use realistic simulated peers rather
than a live unsafe command. Claude's Jetty-specific `send_images`/`send_video` MCP
bridge is not installed into Codex. Rich subagent timelines, secret questions,
MCP elicitation, and new permission request variants are unsupported; unsupported
server requests receive a protocol error instead of silently approving or hanging.
