The shape of it:

- **A bot's chat is a thread whose id is the bot's id.** The client reads it with the existing
  `thread.subscribe`, stops it with `turn.interrupt`, and answers its questions and approvals with
  `question.respond` / `approval.respond`, all with `threadId = bot.id`. Jett's messages go
  through `bot.send`, because the bot's loadout, access mode and turn routing are the bot's, not
  the composer's. The chat thread never appears in chrome's `threads` list or in any
  `thread.upserted` push.
- **Workers are ordinary threads.** A thread a bot starts has `parentThreadId = bot.id`,
  `createdBy: 'agent'` and `botId = bot.id`; threads below it inherit the same `botId`. Their
  first message is a `user_message` with `from = { threadId: bot.id, title: bot.name }`, so
  `useBot(item.from.threadId)` finds the bot that wrote it.
- **The chat shows a filtered transcript.** `shownInBotChat(item)` is the rule: Jett's own
  messages (no `from`), the bot's non-private text, thread markers, errors, questions and
  approvals. Worker reports, Jetty's wakes and the bot's private notes stay in the transcript,
  unseen. One `assistant_message` is one bubble, however rich (Paper "Bot chat / rich reply"
  [1OJB-0]).
- **The face is derived, not stored.** The server sends `activity`, `needsYou`, `failed` and
  `unread` on each `Bot`; `botFace(bot)` turns them into the sketchpad's `BotState` (plus
  `'error'`). Waiting beats typing and working, which beat error; an unseen reply rests on done
  with the unread dot.

### The client mock

`VITE_BOTS_MOCK=bots` serves five fixture bots, one per face, through the real hooks: Forge
(working, with five workers in the first project, a running turn, markers, a reaction, a reply
quote, a rich reply, and hidden private and relayed items), Wren (an unseen reply, so done with
the dot), Atlas (idle), Probe (waiting on an open question) and Scout (a failed turn).
`VITE_BOTS_MOCK=empty` serves no bots. Sending to a mock bot plays scripted turns in rotation: a
plain reply, a react-only turn, a turn that starts a worker (marker plus a new sidebar thread),
and a react-and-reply. Creating a bot plays the greeting. Every other call reaches the real
server, so run the client against an isolated server (below). Delete the mock when M1 merges.

```sh
VITE_BOTS_MOCK=bots JETTY_SERVER_PORT=<server port> client/node_modules/.bin/vite --port <free port> --strictPort
```

### Isolation

Jett's own servers use ports 5173 and 8787 and the sketchpad 5174, against his real `~/.jetty`.
Never use those ports, never point anything at `~/.jetty`, and never kill a process you didn't
start. Run a server on a free port with a temporary home:

```sh
JETTY_HOME=$(mktemp -d) PORT=<free port> bun run server/src/main.ts      # add JETTY_AGENT=echo for a token-free stack
```

`perf/paper/stack.ts` shows the repo's own way to start an isolated stack (`freePort`, a cloned
home, `startServer`). Real Claude bots work in a temporary `JETTY_HOME`: Claude's auth lives in
`~/.claude`, not in Jetty's home.

## Decisions made for Jett

Jett was away; each of these is the simplest reading of the designs and is easy to revisit.

1. **The bot's chat is a thread with the bot's id**, so turns, queueing, steering, child reports,
   sessions and the event log are the existing machinery. Its project row (below) is a hidden
   project for the bot's home.
2. **Its home is a project row nobody sees.** `threads.project_id` is `NOT NULL` with a foreign
   key, and SQLite can't relax that without rebuilding the table, so each bot's home
   (`JETTY_HOME/bots/<id>`) gets a `projects` row marked with the bot's id, which every project
   listing skips. The chat thread lives in it, so its working directory is the home with no
   adapter changes. A cleaner route is fine if the server builder finds one; the wire doesn't
   care.
3. **Done means an unseen reply.** `botFace` shows done when the bot is idle with an unread
   message: the hops play once when a reply lands unseen, and it rests there with the dot until
   the chat opens.
4. **A turn waiting on Jett is idle**, so the chat never says "Forge is working" while it's
   waiting on him; `needsYou` gives the face its badge.
5. **Each home is its own git repo; `preferences.md` lives beside them** at
   `JETTY_HOME/bots/preferences.md` and isn't versioned in M1.
6. **Questions and approvals in the bot chat use the thread chat's existing cards in M1.** Paper's
   question card A and bot approval card B, the settings sheet and its "Always allowed" rules come
   later.
7. **Retry on a failed turn shows but is disabled** (Paper "Error / failed turn" [1RZ6-0]): the
   server has no retry for bots yet.
8. **Stamps for the bot** use the harness format, a line before every message it receives:
   `[Thu, 8 Oct 2026, 15:41]` (en-AU, 24-hour, the machine's zone).
9. **A reply quote reaches the bot as a markdown blockquote** above the message (first 500
   characters of the quoted bubble).
10. **Sending is seeing:** `bot.send` marks the bot seen, as `bot.markSeen` does.
11. **Bots don't get `send_images` or `send_video` in M1**: the bot chat has no media design yet.
12. **The prompt is used whole.** Tools it names that M1 doesn't build yet (tasks, `add_project`,
    `search_wiki`, `search_threads`, quiet and read-only threads) are simply absent, and
    check-ins, the tidy pass and away-compaction are later milestones.

## Server

- [ ] **Bot records.** A `bots` table (migration after `030`): id, name, shape, color, provider,
      model, effort, fast, project_id (nullable, `ON DELETE SET NULL`), permission_mode,
      created_at, seen_at. `threads` gains `bot_id`. _BN: A bot's project is a default, never a
      fence; v1 ships Claude bots only._
- [ ] **`bot.create`** validates (provider `claude`, a model in the catalog, no `max` effort, a
      known project or null), is idempotent on its id (the client resends after a dropped
      connection), and answers `{ bot }`. It creates the home, the chat thread (title = bot name,
      loadout and access mode from the bot) and starts the creation wake: a hidden `user_message`
      from `{ threadId: bot.id, title: 'Jetty' }` saying "{user} just created you.", which counts
      as Jett's turn, so the greeting is visible. _BN: Private text ("and the creation wake, which
      counts as {user}'s")._ Paper "Create / first message" [1TJ7-0].
- [ ] **The home.** `JETTY_HOME/bots/<id>/` with `brief.md` and `index.md` (both empty),
      `pages/`, `log/`, `files/`, and a `CLAUDE.md` holding `@brief.md`, `@index.md` and
      `@../preferences.md`, so Claude loads all three at session start and after compaction (the
      harness's `setup.ts` does exactly this). Create `JETTY_HOME/bots/preferences.md` if missing.
      `git init` and an initial commit. Commit as `-c user.name=Jetty -c user.email=jetty@localhost`
      so no global git identity is needed. Verify `@../preferences.md` actually loads (it's outside
      the home). _Prompt: Wiki; BN: Each bot's home is a git repo._
- [ ] **Commit after every turn that changed the home**: when the chat thread's turn ends
      (completed, failed or interrupted), `git add -A` and commit only if something is staged.
- [ ] **One long-lived Claude session per bot.** The chat thread's provider session is resumed by
      id for the bot's whole life and never rotated; the warm process may idle out and resume like
      any thread's. Options: cwd = the home; `systemPrompt: { type: 'preset', preset: 'claude_code',
append }` where append is Jetty's base instructions without the `mark_ready_for_review`
      sentence (as `harness-v2/jetty.ts` does), the agent-behaviour lines, then the filled bot
      prompt; `additionalDirectories: [JETTY_HOME/bots, ...project paths]` (the bot's project, or
      every project when it has none); model, effort and fast from the bot; `permissionMode` from the
      bot (`auto` or `full_access`); `AskUserQuestion` stays enabled and must be in the
      non-deferred tool set (check the init message's tool list). _BN: A bot's project ("an extra
      readable directory"); `{questionTool}`._
- [ ] **The prompt.** Copy the text from "## You" up to the `---` before "## Build notes" into
      the server (e.g. `server/src/bot-prompt.ts`) verbatim, and fill it when the session starts:
      `{name}`; `{user}` (`oauthAccount.displayName` in `~/.claude.json`, which `provider-usage.ts`
      already reads, else the first word of git's `user.name`, else "the user"); `{home}`; `{bots}`
      (`JETTY_HOME/bots`); `{questionTool}` = `AskUserQuestion`; `{project}` per its three variants
      with `{projects}` / `{others}` as `name (path)` and `~` for the home directory; keep
      `{if auto}` lines only on Auto and `{if full access}` lines only on full access, with the
      marker removed. The system prompt never changes mid-session. _BN: `{project}` is one of;
      `{if full access}`; `{user}`; The system prompt never changes._
- [ ] **Turn routing.** A turn started by `bot.send` or the creation wake is visible: its text
      blocks are ordinary `assistant_message` items. Any other turn (a worker's report or question,
      a restart continuation, an approval) is private: its `assistant_message` items carry
      `private: true`. If `bot.send` lands in a running private turn, the message steers into it and
      text from then on is visible. _BN: Private text._
- [ ] **`tell_user { text }`** (Jetty MCP tool, bots only): appends a visible `assistant_message`
      to the chat, in any turn.
- [ ] **`react { emoji }`** (bots only): one emoji (one grapheme), set as `reaction` on Jett's
      latest message (`item.updated` patch). Its result text is exactly: "If that's your whole reply,
      end your turn now without writing anything. In a turn {user} started, any text you write is
      sent to them as a message." with `{user}` filled. _BN: The `react` tool's result._
- [ ] **Stamps.** Every message delivered to a bot's session starts with a stamp line, e.g.
      `[Thu, 8 Oct 2026, 15:41]` (`toLocaleString('en-AU', { weekday: 'short', day: 'numeric',
month: 'short', year: 'numeric', hour: '2-digit', minute: '2-digit', hour12: false })`), in
      the agent text only, never in the item's text: `agentText` in `orchestrator.ts` is where
      attachment paths are added. _BN: Every message a bot receives is stamped._
- [ ] **`bot.send`** appends the `user_message` (id = `messageId`; with `replyTo: { itemId, text }`
      copied from the quoted chat item when given), starts a turn or steers the running one, and
      marks the bot seen. A repeated `messageId` is a no-op. The reply quote reaches the agent as a
      blockquote above the text. Paper "Message actions A · Floating buttons" [2VG4-0] steps 4–5.
- [ ] **`bot.markSeen`** sets `seen_at` to now.
- [ ] **Live state on each `Bot`**, pushed as `bot.upserted` whenever it changes:
  - `activity`: `idle` with no active turn, or when the active turn waits on Jett; `tidying`
    while a compaction item runs in the chat; `working` through a private turn; in a visible
    turn, `working` while its newest top-level item is a running tool call, subagent or
    workflow (not `tell_user` / `react`), else `typing`.
  - `needsYou`: an unanswered question or undecided approval in the chat, or any thread with
    this `botId` in `awaiting_approval`. _BN: Needs-you face._
  - `failed`: the chat's last turn outcome is `failed`.
  - `unread`: not mid-turn, and the chat has a shown bot message newer than `seen_at`.
    Sketchpad `/components/bot-unread` (a new turn hides the dot until it ends).
- [ ] **Chrome.** The snapshot carries `bots` (oldest first); bot chat threads are left out of
      `threads` and of every `thread.upserted`; worker `ThreadMeta` carries `botId`; projects that
      are bot homes are left out of `projects` and every project listing (chrome, `matchProject`,
      the prompt's project list).
- [ ] **create_thread from a bot.** Defaults to the bot's project; with none, it requires
      `project` and the error lists the names. The new thread is visible (ordinary), owned by the
      bot (`botId`), and the bot's chat gets a `thread_marker` item `{ action: 'started', threadId,
title }`. `send_message` from the bot to a thread adds `{ action: 'messaged' }`. Workers'
      own `create_thread` calls inherit `botId`. _Paper "Messages / markers" [1TPH-0], "Bot ⇄ thread
      / lines" [2RU2-0]._
- [ ] **Restrictions for the bot's own session** (not its workers): `list_models` leaves out
      `max`; `create_thread` and Agent calls refuse `max` ("max isn't available to bots; use
      xhigh"); no `link_pull_request`, `mark_ready_for_review`, `ask_parent`, `send_images` or
      `send_video`; `gh pr view` in the bot's own session never links a pull request to it.
      _BN: Bots don't get; Subagent model and effort._
- [ ] **Depth cap.** In `mcp.ts`, `lineageDepth(caller) >= 2` becomes `>= 3` for everyone, with
      the error and the `create_thread` description saying three levels. _BN: Depth cap._
- [ ] **Echo agent.** With `JETTY_AGENT=echo`, a bot can still be created and replies (its echo
      text is a visible bubble), so the UI can be clicked through without tokens.
- [ ] Remove the `bot.*` stubs in `ws.ts`. Tests only where they freeze what the build notes pin:
      the react result text, private versus visible routing, the depth cap, `max` refused for bots,
      and the tools bots don't get.

   bot in its colour; opening it shows "<face> <bot> / title" and the bot's brief as the first

15. **Nothing leaks.** No bot chat thread appears in Today/Yesterday, search or the command
    palette; no bot home appears as a project anywhere.

## Addendum (Jett, 2026-10-08): an "Accent" bot colour

Added after the builders started, so the integrator owns making both sides line up.

- Client: the face popover's colour choices (New bot, and bot settings when it exists) get an "Accent" option, first among the swatches, drawn in the current accent. A bot set to it follows the user's accent at render time, including wallpaper accents: face, light-mode ink and bubble colour all come from the accent tokens, so changing the accent recolours it with nothing to update. No sketchpad design; design it in the app for Jett to review.
- Server and shared types: a bot's colour may be the value "accent"; accept and store it like any other colour.
- Acceptance: create a bot with Accent, change the app's accent in settings, and the bot's face, sidebar row and chat bubbles all follow it in dark and light.
