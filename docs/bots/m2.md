# Bots v1 · M2 Quiet threads

M2 lets a bot hand off small jobs without filling Jett's sidebar and chat: a quiet thread stays
out of sight until it needs him, a read-only thread reads a project without touching it, and a
quiet thread can be waited on, so its answer lands inside the bot's own turn. It also adds
create_thread's `setup_worktrees`, the muted link to a quiet thread, and puts the parked prompt
lines for all of it back. Claude bots only; workers still run on any provider.

## The contract

On branch `bots/m2-contract`:

| What                                                                                                                               | Where                                                       |
| ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `ThreadMeta.quiet`, `ThreadMeta.readOnly`                                                                                          | `shared/src/wire.ts`                                        |
| `worktreeSetupPrompt(guide)`, now also used by the new-thread page's Set up worktrees                                              | `shared/src/wire.ts`                                        |
| `thread.markSeen` and `thread.pin` surface a quiet thread (no new methods)                                                         | `shared/src/wire.ts` (`methods`)                            |
| create_thread's bot options and wait result: `QuietThreadOptions`, `WaitedThread`, `WAIT_CAP_MS`, `WAIT_PROGRESS_MS`, `WAIT_NOTES` | `shared/src/bots.ts`                                        |
| `ThreadPatch.quiet`; `useMarkThreadSeen` and `usePinThread` surface a quiet thread at once                                         | `client/src/state/chrome.ts`, `mutations.ts`                |
| `useSidebarList()` threads carry `quiet`                                                                                           | `client/src/state/sidebar.ts`                               |
| The mock: `VITE_BOTS_MOCK=quiet`                                                                                                   | `client/src/state/quiet_mock.ts`, switch in `connection.ts` |

The shape of it:

- **Quiet is a flag on the thread, and it only ever clears.** `ThreadMeta.quiet` is `true` while
  the thread is quiet and absent once it surfaces; nothing sets it again. Quiet threads ride
  chrome like any other thread (snapshot and `thread.upserted`), so the client decides where they
  show. `readOnly` is set at creation and never changes.
- **Markers are written as before.** The server still adds `started` and `messaged` markers for a
  quiet thread. The bot chat hides a marker while its thread is quiet, so once the thread
  surfaces its marker shows where it was started, as if it had been visible all along.
- **Opening is seeing.** Jett opening a quiet thread calls `thread.markSeen`, and pinning one
  calls `thread.pin`; the server surfaces it on either. The client hooks patch `quiet: false`
  first, so the row moves in the same frame.
- **The new create_thread options are a bot's own.** They're registered only in a bot's own
  session; workers and ordinary threads keep today's schema.

### The mock

`VITE_BOTS_MOCK=quiet` (set when starting Vite) adds a bot, Forge, beside the real ones, with
five workers in the first project:

- three quiet ones: a read-only lookup and a typo fix, both done, and a version bump that's
  running and surfaces 15 seconds after load by asking for approval (Forge's face goes to
  waiting, its marker appears, and Forge links it in a new bubble);
- one ordinary worker, running;
- one `setup_worktrees` thread in the project checkout, done.

Forge's chat holds a marker for every worker, quiet ones included, as the server writes them, and
a bubble linking the quiet lookup ("which thread looked that up?"). Opening or pinning a quiet
worker surfaces it. Each message to Forge starts a new quiet read-only thread that Forge "waits"
on for four seconds (face working, no marker shown), then it answers. Approving the bump finishes
it. Traffic for Forge and its workers stays in the tab; everything else reaches the real server.
The integrator deletes the mock and its switch.

## Decisions made for Jett

Jett was asleep; each is the simplest reading of the build notes and easy to revisit.

1. **The four options are the bot's own.** `quiet`, `read_only`, `wait` and `setup_worktrees`
   appear only in a bot's own create_thread. Workers and ordinary threads don't get them, so
   their behaviour doesn't change.
2. **Quiet clears for good.** A surfaced thread is an ordinary thread; reopening or unpinning it
   never hides it again.
3. **Markers stay on the server; the client hides quiet ones** (see the contract). A surfaced
   thread's marker appears where it was started, not when it surfaced.
4. **No new RPC.** Opening a quiet thread is `thread.markSeen`; pinning is `thread.pin`.
5. **"Show quiet threads" works like "Show archived".** Off by default, remembered with the other
   sidebar view settings. When on, quiet threads sit in a "Quiet" group after the ordinary groups
   and before Archived, whatever the grouping. A search shows matching quiet threads in that
   group even when it's off (_BN: Quiet threads_: "Quiet threads live in the bot's pane and in
   search").
6. **A quiet change works in its own worktree and pushes to the default branch.** The worktree
   starts from origin's default branch, as a bot's workers already do; Jetty tells the worker to
   push its commits with `git push origin HEAD:<branch>` and never open a pull request. Jetty
   doesn't check branch protection: a refused push comes back in the worker's report, and the bot
   tells Jett. A project with no origin gets no quiet changes (create_thread refuses). The
   worktree's own local branch is an implementation detail; nothing is pushed to it.
7. **Read-only per provider.** Claude: the file-editing tools are removed. Codex: the
   `read-only` sandbox with approval policy `never`. Grok: `--sandbox read-only`, a
   kernel-enforced profile Grok documents (`~/.grok/docs/user-guide/18-sandbox.md`), simpler and
   stronger than the approval-hook refusal the build note suggested. Bash still runs on Claude,
   so Jetty also tells the agent not to write.
8. **A wait comes back early in two more cases**: when the thread needs Jett (so the bot can tell
   him, as it does for any worker's approval), and when Jett messages the bot (Claude Code holds
   a steered message until the running tool call returns, so the bot would otherwise ignore him
   for up to ten minutes). Both return the "still running" kind of result; the report arrives
   after the turn as usual.
9. **wait is on create_thread only.** The build note gives it to create_thread; a follow-up sent
   to an existing quiet thread with send_message reports after the turn, like any other.
10. **The bot's pane isn't built yet** (Paper "Pane / overview" [1U9P-0]); no milestone so far
    builds it. Until it lands, quiet threads reach Jett through "Show quiet threads" and search.
11. **A read-only thread says so in its footer's tooltip** ("Read-only" under "Current
    checkout"), the one place the thread view names its environment. No design exists.
12. **Quiet and read-only threads never claim a pull request by looking at it.** `gh pr view`
    already never claims one for a bot; a quiet thread that claimed one would surface for nothing.
    `gh pr create` still links (and surfaces) as before.
13. **setup_worktrees threads are always visible** and can't be read-only or waited on: they
    change the project checkout, and Jett may want to watch.
14. **M1 follow-ups were already on main**: the done face plays once and settles to idle with the
    dot alone meaning unseen (commit 86eab427), and `preferences.md` lives in its own git repo at
    `JETTY_HOME/bots/shared/`, committed after every bot turn and before every prompt render
    (8dd85d6b), with the prompt's `{bots}/shared/preferences.md` pointing at it. The tidy pass
    isn't in the repo yet: when M5 ports `longsim/prompts/tidy.md`, its path becomes
    `{bots}/shared/preferences.md` (the scratch copy keeps `{bots}/preferences.md`, which the
    longsim harness still uses).

- [ ] **Store.** Migration `034_quiet_threads` (after M6's `033_bot_tasks`):

      and `lands_on TEXT` (the branch a quiet change pushes to; null otherwise). `ThreadMeta`
      carries `quiet: true` and `readOnly: true` only when set. All three survive restarts.
- [ ] **create_thread's bot options.** Register these fields in create_thread's input only when

      handler's input against `QuietThreadOptions`. _BN: Quiet threads; create_thread gains
      `setup_worktrees`._
  - `quiet`: "Keep it out of the user's sidebar and your chat until it needs them (an approval, a
    question, a failure), opens a pull request, or they open it. A quiet change lands straight on
    the project's default branch: it works in a worktree from origin's default branch and pushes
    there, with no branch or pull request of its own."
  - `read_only`: "Read without changing anything: it runs in the project checkout with no
    worktree, and can't edit files. Always quiet."
  - `wait`: "Quiet threads only. Wait for its turn to end and get its final message back as this

- [ ] **Validation**, before anything is created, with exactly these errors (`{project}` is the

  - `wait` without `quiet` or `read_only`: "wait is only for quiet threads: pass quiet or

  - `read_only` with `environment` or `ref`: "A read-only thread reads the project checkout, so

  - a quiet change (`quiet` without `read_only`) with `environment` or `ref`: "A quiet change

- [ ] **wait.** With `wait`, create_thread creates and starts the thread as usual, then holds the
      call. _BN: Quiet threads (`wait`)._ It returns `WaitedThread` (`shared/src/bots.ts`), the

    `store.reportSettledChild` uses to deliver a report (its turn from the bot has ended, nothing
    queued, no running subagent or workflow holding the report). `report` is the final message
    the relayed report would carry (capped at `REPORT_CAP`), `error` the failure. Mark the report
    delivered (`orchestration_requests` `report:<thread>:<turn>`, as `suppressReport` does) so it
    isn't relayed again after the turn.

    twice.
  - `needs_user`: the moment the thread surfaces for needing Jett (approval, question or

  - `running`, `detail` = `WAIT_NOTES.running` (the build note's text, verbatim): after

    the bot's turn does. The thread carries on and reports after the turn as usual.
  - A retried call with the same `requestId` returns the stored creation result without waiting.

## Acceptance checks (QA clicks through these)

Run against an isolated stack with the real Claude agent (a second pass with `JETTY_AGENT=echo`
and the mock for the UI-only checks). One git project whose `origin` is a local bare repo, so a
quiet change can push without GitHub; no `.jetty/worktree.json` in it at first. Light and dark.
Read the bot's tool calls in its transcript (the chat thread's items) to see what it chose.

1. **Prompt.** The bot's `.jetty/instructions/workers.md` and `lookups.md` contain the five
   restored lines exactly as the build notes park them; the search line is still absent.
2. **Setup worker.** Ask the bot for a change in the project. It starts a setup worker with
   `setup_worktrees`: a visible thread in Current checkout, "Started Set up worktrees" in the
   chat, first message exactly "Set up Jetty worktrees for this project. Read <path to
   docs/worktree-setup.md> and follow it." Once the file exists, another `setup_worktrees` call is
   refused with "<project> is already set up for worktrees."
3. **Quiet read.** Ask something that needs reading the code ("where is X configured?"). The bot
   starts a read-only thread with `wait`: no marker, no sidebar row, the face shows working, and
   the answer arrives in the same turn and matches the code.
4. **Read-only holds.** That thread's environment is Current checkout and its footer tooltip
   says Read-only. Open it and ask it to add a line to the README: it can't (no Edit or Write
   tool) and says so, and `git status` in the project checkout is unchanged.
5. **Show quiet threads.** The filter menu has the switch, below Show archived. On, the read-only
   thread sits in a "Quiet" group above Archived; off, it's gone; the setting survives a reload.
   Typing part of its title in Search threads shows it with the switch off.
6. **Quiet change.** Ask for a one-line fix. The bot starts a quiet thread with `wait`; its
   commit lands on origin's default branch in the bare repo, no other branch is pushed, no pull
   request is opened, and the bot reports it in the same turn. Nothing shows in the sidebar or
   chat.
7. **Muted link.** Ask "which thread did that?". The bot links it; the link's title is muted
   with a live status glyph. Clicking it opens the thread, which then appears in its ordinary
   sidebar group and gets its marker in the chat; the link turns accent.
8. **Pin surfaces.** With Show quiet threads on, pin a quiet thread: it moves to Pinned and stays
   visible after unpinning.
9. **Needs Jett.** Get a quiet thread to ask for approval (e.g. a quiet change whose command
   Claude's auto mode stops to ask about; the mock's version bump shows the same thing without
   tokens). It appears in the sidebar at once with the amber
   glyph, its marker appears in the chat, the bot's face shows waiting, and the bot tells Jett
   what it wants with a link to it (its wait returned `needs_user`).
10. **Jett interrupts a wait.** While the bot waits on a slow read (a broad question over the
    whole repo), send it a message: it answers within seconds, and the read's report reaches it
    after the turn.
11. **Parallel reads.** Ask two unrelated questions at once. Two read-only threads start within a
    couple of seconds of each other, and both answers arrive in the same turn.
12. **Long wait.** A read that takes over a minute still returns its answer through the call (no
    tool timeout); the server sent progress notifications.
13. **Refusals.** In the bot's transcript or via a test bot prompt: `wait` without quiet, a
    read-only thread with a ref, a quiet change in a project with no origin, and
    `setup_worktrees` with a prompt each fail with the contract's exact error.
14. **Not for workers.** A worker's create_thread (and an ordinary thread's) has no quiet,
    read_only, wait or setup_worktrees.
15. **Restart.** Restart the server: quiet threads stay quiet, surfaced ones stay visible, and a
    read-only thread resumed afterwards still has no editing tools.
16. **M1 follow-ups.** A turn that ends with a reply plays the done face once and settles to idle
    with the dot; `JETTY_HOME/bots/shared` is a git repo whose log gains a commit when a bot saves
    a shared preference.
