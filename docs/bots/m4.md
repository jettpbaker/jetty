# Bots v1 · M4 Search

M4 gives every bot two search tools: `search_wiki` over its own wiki home, and `search_threads`
over its chat and its workers' threads. Both mix BM25 keyword scores with EmbeddingGemma embedding
similarity, run the model on this machine in a child process, and index incrementally. Claude bots
only, like the rest of v1. M4 adds no UI.

Sources, in order of authority:

- **Build notes**: `~/code/scratch/bots/bot-prompt.md`, section "Build notes (not prompt text)".
  Cited below as _BN: <first words of the note or sub-bullet>_. The M4 note is "search_wiki and
  search_threads (Jett's call 2026-10-08)" and its sub-bullets; the prompt line comes from "Prompt
  lines waiting on M2–M4".
- **The recall library**: `~/code/scratch/bots/longsim/recall` (`README.md`, `lib.ts`, `embed.ts`,
  `chunk.ts`, `walk.ts`, `bm25.ts`, `vec.ts`). It's the implementation the build notes name and
  benchmark; port it, don't redesign it. `~/code/scratch/bots/longsim/harness-recall/memory-search.ts`
  shows it wired into a bot as an MCP tool (reference only: a one-shot `reindex` + `recall` per call,
  in process, which M4 replaces with the child process).
- **Sketchpad and Paper**: no sketchpad route and no board on Paper's "Bots v1 — flows (Oct 7)" page
  covers search (checked: the only "search" on that page is the sidebar's Search threads row). The
  bot chat never shows tool calls (`shownInBotChat` in `shared/src/bots.ts`), so a search shows as
  the working face and "<name> is working", which M1 already does.

## The contract

On branch `bots/m4-contract`:

| What                                                                                     | Where                                         |
| ---------------------------------------------------------------------------------------- | --------------------------------------------- |
| Tool descriptions (verbatim from the build notes), `k` default and cap, query length cap | `shared/src/bot-search.ts`                    |
| Tool input `SearchInput` and results `SearchResults<WikiSearchHit \| ThreadSearchHit>`   | `shared/src/bot-search.ts`                    |
| The search line restored in the bot prompt                                               | `server/src/bot-prompt/lookups.md` (bullet 1) |

Nothing in M4 crosses the client wire: the tools are Jetty MCP tools whose JSON results go to the
bot's agent only. There is no client mock, because there is nothing for a client to build against.

The shape of it:

- **Two tools, not one.** Threads will far outnumber wiki pages, so a combined ranking would bury
  the durable pages. _BN: Two tools, not one._
- **The model lives in a child process.** One child serves every bot. It starts on the first search
  and exits after 5 idle minutes, so its ~410MB comes back in full and the server's memory never
  holds the model. It downloads the weights (316MB) once, into `JETTY_HOME/models/`. _BN: The model
  runs in its own child process._
- **Indexes are per bot**, at `JETTY_HOME/search/<botId>.sqlite`, outside the bot's home (which is
  the bot's own git repo, and the agent can write to it). They catch up at search time: wiki files by
  content hash, thread messages by id. _BN: Indexing is incremental._
- **The child does the heavy lifting**: embedding, the SQLite reads and writes, and ranking. The
  server gathers thread messages from its store, sends the new ones over, and formats the results,
  so a search never blocks the server's event loop on BM25 over thousands of chunks.

### Isolation

Jett's own servers use ports 5173 and 8787 and the sketchpad 5174, against his real `~/.jetty`.
Never use those ports, never point anything at `~/.jetty`, and never kill a process you didn't
start. Run a server on a free port with a temporary home:

```sh
JETTY_HOME=$(mktemp -d) PORT=<free port> bun run server/src/main.ts      # add JETTY_AGENT=echo for a token-free stack
```

`perf/paper/stack.ts` shows the repo's own way to start an isolated stack (`freePort`, a cloned
home, `startServer`). Real Claude bots work in a temporary `JETTY_HOME`: Claude's auth lives in
`~/.claude`, not in Jetty's home.

Every temporary home would download the 316MB weights again. To skip that, clone the copy the
recall library already has (APFS clone, no extra disk):

```sh
mkdir -p "$JETTY_HOME/models" && cp -cR ~/code/scratch/bots/longsim/recall/.cache/onnx-community "$JETTY_HOME/models/"
```

Acceptance check 2 is the one run that must start with an empty `models/` and download for real.

## Decisions made for Jett

Jett was asleep; each is the simplest reading of the build notes and easy to revisit.

1. **The child owns indexing and ranking**, not only embedding, so neither the model nor a large
   ranking pass touches the server process.
2. **One child for all bots, 5 idle minutes**, requests served one at a time. The build notes say "a
   few idle minutes".
3. **Index files at `JETTY_HOME/search/<botId>.sqlite`, weights at `JETTY_HOME/models/`.** Deleting
   a bot, once that exists, removes its index file too.
4. **Indexes catch up only when a search runs.** No background indexing after turns: it would keep
   the child (and its 410MB) alive whenever Jett is active. The cost is a slower first search after a
   long stretch, and a one-off backfill for a bot that already has history.
5. **What search_threads covers**: the bot's chat and every thread with its `botId` (workers, their
   children, M2's quiet threads), archived ones included and flagged, deleted ones gone. Indexed
   messages: the main timeline's `user_message` and `assistant_message` items, once complete, except
   the bot's private notes, report messages (their text is the worker's final message, which is
   indexed in the worker's own thread, so it would otherwise show twice) and Jetty's own notes
   (restart notes, PR news, the creation wake, later check-ins: every `from` whose `threadId` is the
   thread it's in). Check-ins would otherwise add a near-identical chunk every hour.
6. **Results**: the hit shapes in `shared/src/bot-search.ts`. The bot's own chat reads as thread
   "your chat" with no link (it has no thread page); every other hit carries `jetty://threads/<id>`.
   Dates use the bot stamp's format, so they read like the stamps on its messages.
7. **`k` defaults to 5 and stops at 20**; a query is 1–1,000 characters.
8. **A search waits up to 60 seconds for the model**, then answers with a "not ready" error while
   the download carries on (wording below; Claude to confirm, since tool results are harness
   wording).
9. **Both tools never ask for approval**: they're added to `SELF_TOOLS` with the other read-only
   tools.
10. **The prompt's stand-in line goes.** `lookups.md` bullet 1 was M1's stand-in for the parked
    line ("Check your wiki for what you know. list_threads finds a thread and read_thread opens
    it."); the parked line replaces it word for word. M2 restores bullet 2 ("Hand reading off…") in
    the same file, so the two branches touch adjacent lines and a rebase may stop on a trivial
    conflict: keep both restored lines.

## Server

- [ ] **Port recall into the server**, e.g. `server/src/search/` (`bm25.ts`, `chunk.ts`, `walk.ts`,
      `vec.ts`, and the index and rank logic from `lib.ts`), in repo style (oxfmt, oxlint, `type`,
      `function` declarations, `for...of`, no classes). Keep its behaviour exactly: which files count
      (`walk.ts`: `brief.md`, `index.md`, `preferences.md` at the root, markdown under `pages/` and
      `log/`, text files under `files/`, nothing with a null byte in its first 8KB, no dot entries, no
      symlinks), the chunking rules (`chunk.ts`), the model card prompts, the 768-dim l2-normalised
      vectors as float32 blobs, the score `0.7 × clamp(cosine, 0, 1) + 0.3 × bm25 / (bm25 + 8)` with
      BM25 k1 1.2, b 0.75, its stop list and plural stem, and the tie-break order. Keep its unit tests
      that pin chunking and ranking (`chunk.test.ts`, the ranking parts of `search.test.ts`) with a
      fake embedder. _BN: Built from the overnight recall library._
- [ ] **Dependency**: `@huggingface/transformers` (`^4.3.1`, as recall has it) in `server/package.json`,
      and whatever `trustedDependencies` its `onnxruntime-node` needs in the root `package.json`
      (recall lists `onnxruntime-node` and `protobufjs`). `bun install` must work from a clean clone.
- [ ] **The child process.** An entry file (e.g. `server/src/search/child.ts`) run as
      `Bun.spawn([process.execPath, <that file>])` with an IPC channel (Bun's `ipc`, or JSON lines on
      stdio like `stdio-rpc.ts`). It loads `onnx-community/embeddinggemma-300m-ONNX`, dtype `q8`,
      on CPU, with `env.cacheDir = JETTY_HOME/models`, runs recall's self-check (Mars must rank first)
      once per start, and refuses to index if that fails. Requirements:
  - started on the first search, shared by every bot, serving one request at a time;
  - exits after 5 minutes with no request; the next search starts a fresh one;
  - never outlives the server: it exits when the server exits or its IPC channel closes, including a
    `--watch` restart or a killed server;
  - a child that crashes fails the request it was serving with a tool error; the next search starts a
    new child;
  - its stderr goes to the server's log, and each index pass logs one line with its counts (files or
    messages embedded, unchanged, removed, chunks, milliseconds), which is how QA checks that
    indexing is incremental.
    _BN: The model runs in its own child process; Weights (316MB) download once into JETTY_HOME._
- [ ] **Waiting for the model.** A search waits up to 60 seconds for the child to have the model
      loaded (the first download can take longer). Past that, or if loading fails, the tool returns an
      error result (`isError`) and the download carries on for the next search:
  - search_wiki: "Search isn't ready: {reason}. Read your index.md or grep your pages meanwhile."
  - search_threads: "Search isn't ready: {reason}. Use list_threads and read_thread meanwhile."
  - `{reason}` is "its model is still downloading (45% of 316 MB)" while downloading, else the
    load error's first line.
- [ ] **Index files.** One SQLite file per bot at `JETTY_HOME/search/<botId>.sqlite`, opened by the
      child with `bun:sqlite` (WAL), holding the wiki index (recall's `files` and `chunks` tables and
      `meta`, with the embedder id `onnx-community/embeddinggemma-300m-ONNX@q8`, so a changed embedder
      re-embeds) and the thread index (per message: id, thread id, author, created at; per chunk:
      message id, text, vector). Searches for the same bot are serialised (the agent calls tools in
      parallel; `memory-search.ts` shows the same guard).
- [ ] **`search_wiki { query, k? }`** (bots only; `inputSchema` `query` 1–`SEARCH_QUERY_MAX`
      characters, `k` an integer 1–`SEARCH_MAX_K`, default `SEARCH_DEFAULT_K`; description
      `SEARCH_WIKI_DESCRIPTION`). The home is the bot chat thread's project path
      (`JETTY_HOME/bots/<id>`). The child re-indexes it (files whose sha256 and embedder id match are
      skipped, removed files dropped) and returns the top k as `SearchResults<WikiSearchHit>`, paths
      relative to the home. _BN: search_wiki; Indexing is incremental._
- [ ] **`search_threads { query, k? }`** (bots only; same input; description
      `SEARCH_THREADS_DESCRIPTION`):
  - Scope: threads whose `bot_id` is the bot (its chat thread has its own id as `bot_id`), archived
    included, deleted gone. Chunks of threads no longer in scope are dropped on the next search.
  - Messages: decision 5. Skip messages still streaming; a later search picks them up.
  - Author: a `user_message` with no `from` is `{user}` (`botUserName()` in `bot-home.ts`); with
    `from`, it's `from.title` (a bot's chat is titled with the bot's name, a worker with its own
    title). An `assistant_message` is the bot's name in its chat, else the thread's title.
  - Chunks: the message text through recall's prose chunker; embed with the thread's title as the
    document title and "From {author}, {date}" as context, the way recall prepends a page's tags. The
    hit's `text` is the message text only.
  - Incremental: a message is embedded once, by id, and never again after a restart. A thread whose
    state hasn't changed since the last pass (its `lastSeq`) costs neither a state load nor a send to
    the child.
  - Results: `SearchResults<ThreadSearchHit>`. `thread` is the thread's current title, or "your chat"
    for the bot's own; `link` is `jetty://threads/<id>` except for its own chat; `archived: true` on
    archived threads; `date` is the message's `createdAt` in `botStamp()`'s format without brackets
    (give `botStamp` a date argument rather than copying it).
    _BN: search_threads; Indexing is incremental._
- [ ] **Registration** in `mcp.ts` inside `if (bot)`, with `toolMeta` like every bot tool, so both
      load without ToolSearch. Workers and ordinary threads never get them. Add both names to
      `SELF_TOOLS` in `jetty-tools.ts` so they never ask for approval.
- [ ] **Tests** only where they freeze what the build notes pin, all with a fake embedder (no model
      download, no child process in `bun test`): both descriptions verbatim and bots-only registration
      (extend "bots only receive their own safe tools" in `mcp.test.ts`); `k` defaults to 5;
      incremental indexing (an unchanged home re-embeds nothing, one changed page re-embeds only that
      file, and a second search_threads embeds only new messages); and scope (another bot's threads,
      Jett's own threads, private notes and report messages never come back).
- [ ] Check by hand once with the real model on an isolated stack: the self-check passes, a search
      answers, the child's RSS holds the model while the server's doesn't grow by it, and the child
      exits 5 idle minutes later.

## Client

Nothing to build. The results go to the bot's agent; the bot chat hides tool calls and already
shows the working face and "<name> is working" while any tool runs; thread links the bot writes from
a hit (including an archived worker) are the ordinary `jetty://threads/<id>` entity links. A search
UI, a model download indicator or a setting would be new design, and none exists in the sketchpad,
Paper or the build notes.

## Acceptance checks (QA clicks through these)

Run against an isolated stack with the real Claude agent (Sonnet 5.5 for most, then a pass on
Opus 5.5), one git project added. Seed `models/` as above except for check 2. The bot's tool calls
don't show in its chat: read them from its thread (`thread.subscribe` on the bot's id, or the
`thread_states` row in `JETTY_HOME/jetty.db`).

1. **Tools and prompt.** A new bot's session lists `mcp__jetty__search_wiki` and
   `mcp__jetty__search_threads` among its loaded tools (no ToolSearch needed), with the build notes'
   descriptions word for word; a worker's session has neither. `JETTY_HOME/bots/<id>/.jetty/instructions/lookups.md`
   starts with "Search before you fan out: search_wiki for what you know, search_threads for what was
   said and when. read_thread opens a thread." Neither tool asks for approval, on Auto or Full access.
2. **First download.** With an empty `JETTY_HOME/models/`, the first search downloads about 316MB
   there and answers (if it takes over a minute, the tool returns "Search isn't ready: its model is
   still downloading (N% of 316 MB)…" and a later search answers). Restart the server and search
   again: nothing downloads.
3. **Wiki recall.** Tell the bot a specific fact worth keeping (e.g. "releases moved to Thursdays
   because of exam prep"); once its page exists, start a fresh topic and ask "what day do we release
   and why?". The bot calls search_wiki, the top hit is the page with its path and line range, and
   the answer is right.
4. **Thread recall.** Have a worker do something with a distinctive detail (an error code, a file
   name), then ask the bot "which thread ran into <detail>, and when?". The bot calls
   search_threads; the hit carries the worker's title, its author and a date in the stamp format; the
   bot's reply links the worker, and the link opens it.
5. **Incremental.** The server log shows a second search with nothing changed embedding nothing;
   after the bot edits one page, only that file re-embeds; after a worker's new turn, only its new
   messages embed. Restart the server: the next search embeds nothing it had already embedded.
6. **Scope.** With two bots, neither finds the other's workers or chat; Jett's own (bot-less)
   threads never come back; the bot's private notes and the report messages in its chat never come
   back (a worker's final message appears once, from the worker's thread); Jetty's notes (restart,
   PR news, the creation wake) never come back. An archived worker still comes back, flagged
   `archived`.
7. **The process.** After a search, one child `bun` process holds the model (~400MB RSS) and the
   server's own RSS hasn't grown by that; it exits about 5 minutes after the last search, and the next
   search starts a new one. Stopping the server (Ctrl-C, and separately `kill -9` of the server you
   started) leaves no child behind.
8. **Parallel calls.** Ask something that makes the bot call both tools in one response: both
   answer, nothing errors.
9. **Not ready.** With no network and an empty `models/`, a search returns the "Search isn't ready"
   result within about a minute, the bot carries on (reading its pages or threads), nothing crashes,
   and once the network is back the next search downloads and answers.
10. **The chat.** While the bot searches, its chat shows only the working face and "<name> is
    working"; no tool text or result appears in a bubble.
11. **Gates.** `bun run typecheck`, `bun run lint`, `bun run format:check` and `bun test` pass, and
    `bun test` downloads nothing and starts no child process.
